## 1. 概要

### 1.1 目的

本プロジェクトは、Laravelプロジェクトのプルリクエスト作成前に開発者自身がセルフレビューを行うためのCLIツールを開発することを目的とする。既存の静的解析ツールでは検出困難な、文脈依存のコード品質問題を検出し、開発者の気づきを支援する。

### 1.2 背景

Laravelプロジェクトのコードレビューでは、型や構文レベルの問題は静的解析ツールで検出可能である一方、以下の類の問題は検出が難しい。

- 文脈依存のパフォーマンス問題（N+1問題、同期処理の適否等）
- ビジネスロジックの理解が必要なセキュリティリスク（認可漏れ、マスアサインメント等）
- 設計判断を伴う可読性の問題（Fat Controller、責務越境等）

これらは熟練レビュアーの暗黙知に依存しており、セルフレビュー段階での検出が困難である。本ツールはLLMを活用することで、これらの暗黙知を補完する。

### 1.3 スコープ

本プロジェクトの対象範囲は以下の通り。

- Laravelプロジェクトのソースコードを対象としたセルフレビュー機能の提供
- コマンドラインインターフェースによる操作
- ローカル環境での実行を前提とした動作

### 1.4 対象利用者

- Laravel開発に従事する個人開発者および業務開発者
- プルリクエスト作成前のセルフレビューを実施したい開発者
- 既存の静的解析ツールを併用している開発者

## 3. 業務要件

### 3.1 As-Is（現状の業務フロー）

開発者がLaravelプロジェクトのコード変更を行い、プルリクエストを作成するまでの現状フローは以下の通り。

1. 開発者がコードを変更する
2. 開発者が静的解析ツール（PHPStan等）を実行する
3. 開発者が自身の変更内容を目視で確認する
4. 開発者がプルリクエストを作成する
5. 他の開発者がレビューを行う

この現状では以下の課題がある。

- ステップ3の目視確認が属人的であり、観点の漏れが発生しやすい
- 静的解析では検出できない問題が、他の開発者によるレビュー段階（ステップ5）で初めて指摘される
- セルフレビューの品質がレビュー前の手戻り回数に直結する

### 3.2 To-Be（あるべき業務フロー）

本ツール導入後のあるべきフローは以下の通り。

1. 開発者がコードを変更する
2. 開発者が静的解析ツールを実行する
3. **開発者がlrvを実行し、LLMによるレビューを受ける**
4. **開発者がlrvの指摘内容を確認し、必要な修正を行う**
5. 開発者がプルリクエストを作成する
6. 他の開発者がレビューを行う

ステップ3と4の追加により、セルフレビュー段階で文脈依存の問題を検出し、レビュー前の手戻りを削減することを目指す。

### 4.2 機能詳細

#### FR-001 差分取得機能

| 項目 | 内容                                                                          |
| ---- | ----------------------------------------------------------------------------- |
| 概要 | ローカルのGitリポジトリから、現在のブランチとベースブランチ間の差分を取得する |
| 入力 | ベースブランチ名（任意指定）                                                  |
| 出力 | 変更されたファイルのパス一覧、各ファイルの差分内容、各ファイルの全体内容      |
| 条件 | 実行ディレクトリがGitリポジトリ配下であること                                 |

ベースブランチは以下の優先順位で決定する。

1. コマンドオプションで明示的に指定された場合、その指定に従う
2. 指定がない場合、現在のブランチの分岐元を自動検出する
3. 自動検出できない場合、利用者にエラーメッセージを表示し、明示的な指定を促す

この方式により、以下のブランチ戦略に対応可能とする。

- main単一ブランチ戦略（GitHub Flow等）
- develop + main構成（Git Flow等）
- 環境別ブランチ構成（GitLab Flow等）
- カスタムブランチ名を用いる独自構成

#### FR-002 レビュー実行機能

| 項目 | 内容                                                                    |
| ---- | ----------------------------------------------------------------------- |
| 概要 | 取得した差分と変更ファイル全体を入力として、LLMによるレビューを実行する |
| 入力 | 差分情報、変更ファイル全体のコード                                      |
| 出力 | 指摘一覧（ファイル名、行番号、カテゴリ、確信度、内容）                  |

#### FR-003 複数観点並行レビュー機能

| 項目         | 内容                                                                |
| ------------ | ------------------------------------------------------------------- |
| 概要         | パフォーマンス、セキュリティ、設計・可読性の3観点を並行して実行する |
| 期待効果     | 逐次実行に比べて実行時間を短縮する                                  |
| 失敗時の挙動 | いずれかの観点が失敗した場合でも、他の観点の結果を出力する          |

#### FR-004 パフォーマンス観点レビュー

以下の観点で指摘を生成する。

| 検出対象               | 内容                                                      |
| ---------------------- | --------------------------------------------------------- |
| N+1問題                | Eloquentリレーションのループ内呼び出し、Eager Loading漏れ |
| キュー化すべき同期処理 | メール送信・外部API呼び出し・重い処理の同期実行           |

#### FR-005 セキュリティ観点レビュー

以下の観点で指摘を生成する。

| 検出対象                 | 内容                                                  |
| ------------------------ | ----------------------------------------------------- |
| マスアサインメント脆弱性 | $fillable/$guardedの未設定、$request->all()の直接渡し |
| SQLインジェクション      | DB::raw/whereRawでの変数展開                          |
| 認証関連                 | 不適切なパスワード比較、セッション管理の不備          |

#### FR-006 設計・可読性観点レビュー

以下の観点で指摘を生成する。

| 検出対象                 | 内容                                                               |
| ------------------------ | ------------------------------------------------------------------ |
| Fat Controller           | コントローラーへのロジック集中（目安200行以上、1メソッド50行以上） |
| サービスクラスの責務越境 | 1つのServiceが複数の関心事を抱えている                             |
| 深いネスト               | 3段以上の連続ネスト、早期return可能箇所                            |

#### FR-007 確信度判定機能

各指摘に対して、以下の3段階の確信度を付与する。

| 確信度 | 判定基準                                                                   |
| ------ | -------------------------------------------------------------------------- |
| 高     | 明らかなアンチパターン、コード上の証拠が明確、誤検知の可能性がほぼない     |
| 中     | 文脈次第で問題になるパターン、周辺コードから判断している、設計判断が関わる |
| 低     | 推測の要素が強い、実行時の挙動に依存、スタイル・好みに寄った指摘           |

#### FR-008 Markdown出力機能

レビュー結果を以下の構造を持つMarkdown形式で出力する。

- 冒頭に全指摘の確信度別件数サマリー
- 実行対象（ブランチ、ファイル数、実行時刻）の記載
- ファイル単位でのセクション分割
- 各指摘に観点カテゴリ、確信度、行番号、内容、該当コードを明記

#### FR-009 出力先指定機能

| 指定方法                 | 出力先           |
| ------------------------ | ---------------- |
| 指定なし                 | 標準出力         |
| -o / --output オプション | 指定ファイルパス |

#### FR-010 ベースブランチ指定機能

| 指定方法          | ベースブランチ                   |
| ----------------- | -------------------------------- |
| 指定なし          | 現在のブランチの分岐元を自動検出 |
| --base オプション | 指定ブランチ名                   |

#### FR-011 観点絞り込み機能

レビューする観点を絞り込む機能。未指定時は全観点を実行する。

| 指定方法                     | 対象観点               |
| ---------------------------- | ---------------------- |
| --focus=performance          | パフォーマンス観点のみ |
| --focus=security             | セキュリティ観点のみ   |
| --focus=design               | 設計・可読性観点のみ   |
| --focus=performance,security | 複数観点指定           |

## 6. 制約条件

| ID      | 制約内容                                                                     |
| ------- | ---------------------------------------------------------------------------- |
| CON-001 | 実装言語はGoを使用する（学習目的のため）                                     |
| CON-002 | 開発期間は合計2ヶ月（MVP完成まで4〜6週間、残り2〜4週間をバッファ期間とする） |
| CON-003 | 個人開発であり、開発リソースは開発者1名、平日朝1.5時間のみ                   |
| CON-004 | 本ツールはLLMプロバイダの外部APIに依存する                                   |
| CON-005 | LLM利用にかかる費用は利用者が負担する                                        |

## 8. 対象範囲外

| ID      | 対象範囲外項目                           | 理由・備考                                                                 |

## 9. リスク

| ID       | リスク内容                                             | 影響度 | 発生可能性 | 対応方針                                                       |
| -------- | ------------------------------------------------------ | ------ | ---------- | -------------------------------------------------------------- |
| RISK-001 | LLMの応答品質が期待水準に達しない                      | 大     | 中         | プロンプトを段階的に改善する。誤検知は確信度ラベルで緩和する   |
| RISK-002 | LLM APIコストが想定を超過する                          | 中     | 中         | Sonnet系モデルを基本とし、開発中のテスト頻度を管理する         |
| RISK-003 | LLM APIの仕様変更                                      | 中     | 低         | プロバイダ抽象化インターフェースを用意し、変更影響を局所化する |
| RISK-004 | 開発リソース不足によるスコープ未達                     | 中     | 中         | 機能の優先度を明確化し、必須機能のみで一旦完成させる           |
| RISK-005 | 変更ファイル全体のトークン送信によるコスト増           | 中     | 中         | ファイルサイズの上限設定等による対策をフェーズ2で検討          |
| RISK-006 | 利用者のソースコードが外部に送信されるプライバシー懸念 | 大     | -          | READMEでの明示、機密コードでの利用を推奨しない旨を記載         |
| RISK-007 | 学習目的とポートフォリオ目的の両立困難                 | 小     | 低         | 段階的な機能拡張により両立を図る                               |
