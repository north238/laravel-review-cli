## 1. 概要

### 1.1 本ドキュメントの目的

本ドキュメントは、要件定義書・基本設計書・詳細設計書で定義された内容を実装するための、具体的な進め方を定義する。スケジュール、作業分解、進捗管理、リスク対応の観点から、実装フェーズの全体計画を示す。

### 1.2 本プロジェクトの位置づけ

本プロジェクトは、Fumiyaの長期学習計画における「フェーズ1」に相当する。学習目的とポートフォリオ目的の両立を図り、Go言語の実践的習得とAI活用力の向上を同時に目指す。

### 1.3 開発方針

- ウォーターフォール開発のプロセスに準拠する（要件定義→基本設計→詳細設計→実装→テスト）
- ただし、実装フェーズ内では段階的な機能追加とプロンプト改善を許容する
- 最低限動作する状態（MVP）を早期に実現し、その後段階的に磨き込む

## 5. マイルストーン

各マイルストーンの達成条件と確認方法を明示する。

### M1: シングル観点動作（Week 2終了時）

| 項目         | 内容                                                              |
| ------------ | ----------------------------------------------------------------- |
| 達成条件     | パフォーマンス観点（N+1問題）が実プロジェクトで検出できる         |
| 確認方法     | 既知のN+1問題を含むLaravelコードでlrvを実行し、検出結果を目視確認 |
| 失敗時の対応 | プロンプト調整、Week 3着手を遅延                                  |

### M2: コア機能完成（Week 3終了時）

| 項目         | 内容                                                                |
| ------------ | ------------------------------------------------------------------- |
| 達成条件     | 3観点が並行実行され、それぞれの結果が統合されたMarkdownが出力される |
| 確認方法     | 実プロジェクトで実行し、3観点の結果と並行実行の動作確認             |
| 失敗時の対応 | 並行実装を簡略化（逐次実行で代替）、後週にリファクタ                |

### M3: MVP完成（Week 4終了時）

| 項目         | 内容                                                     |
| ------------ | -------------------------------------------------------- |
| 達成条件     | 拡張MVPの仕様（基本設計書記載分）がすべて動作する        |
| 確認方法     | 全オプション組み合わせの動作確認、エラーケースの動作確認 |
| 失敗時の対応 | スコープ縮小、--focusオプション等を後回し                |

### M4: 実用品質到達（Week 6終了時）

| 項目         | 内容                                                             |
| ------------ | ---------------------------------------------------------------- |
| 達成条件     | 自分の業務コードに使って実用に耐える品質、READMEが整備されている |
| 確認方法     | 1週間以上自分のPR作成前に実利用、誤検知率が許容範囲              |
| 失敗時の対応 | プロンプト改善を継続、フェーズ1延長を検討                        |

### M5: フェーズ1完了（Week 8終了時）

| 項目         | 内容                                                  |

## 7. リスク管理

要件定義書のリスク（RISK-001〜007）に加え、実装フェーズ特有のリスクを管理する。

### 7.1 実装フェーズのリスク

| ID       | リスク                                             | 影響度 | 発生可能性 | 対応方針                                                                   |
| -------- | -------------------------------------------------- | ------ | ---------- | -------------------------------------------------------------------------- |
| IRISK-01 | プロンプト品質の調整に想定以上の時間がかかる       | 大     | 高         | Week 5〜6を改善期間として明確に確保。Week 3〜4は最低限の品質で進める       |
| IRISK-02 | LLM APIコストが想定を超える                        | 中     | 中         | 開発中は小さなテストデータで実行、大規模試行はWeek 5以降に集中             |
| IRISK-03 | 並行処理実装で予期せぬバグが発生                   | 中     | 中         | Week 2のシングル観点で逐次動作を確認後、Week 3で並行化する段階的アプローチ |
| IRISK-04 | 朝1.5時間の確保が崩れる                            | 中     | 中         | 週末を予備日として活用、Week 7〜8のバッファで吸収                          |
| IRISK-05 | 想定外の技術的詰まり（Cobraの仕様、context挙動等） | 中     | 中         | 1日詰まったら方針転換。代替案を持つ                                        |
| IRISK-06 | スコープ追加の誘惑（PR要約等を入れたくなる）       | 小     | 高         | 対象範囲外（OUT-001〜010）を厳守、追加はフェーズ2へ                        |
| IRISK-07 | テスト不足で実用段階で品質問題が発覚               | 中     | 中         | Week 5にテスト整備の時間を明示的に確保                                     |

### 7.2 リスク発生時のエスカレーション

個人開発のためエスカレーション先はないが、以下の方針で対応する。

- 1日詰まったら、設計書を見直して方針転換を検討
- 1週間遅延したら、スコープを縮小
- マイルストーン未達が2回続いたら、フェーズ1の延長を検討

## 8. 進捗管理

### 8.1 週次レビュー

毎週末に以下を実施する。

| 観点     | 確認項目                         |
| -------- | -------------------------------- |
| 進捗     | 計画タスクの完了率（％）         |
| 品質     | ビルド成功、動作確認済みの状態か |
| リスク   | 新たなリスクが発生していないか   |
| 学習     | 今週身についた技術、未理解の概念 |
| 次週計画 | 翌週のタスク優先順位の調整       |

### 8.2 週次レビューの記録

別途「週次学習ログ」として記録する（フォーマットは別ドキュメントで定義予定）。

### 8.3 月次振り返り

月に一度、以下の観点で振り返る。

- 当初計画に対する進捗率
- 学習内容のアウトプット（コード、ドキュメント、記事）
- 疲労度と持続可能性の自己評価
- 次月の調整事項
